# Anon Feedback — DevSecOps CI/CD Project

A small full-stack application built primarily as a **DevSecOps learning project**.

The application itself is intentionally simple. The main goal is the CI/CD pipeline around it: static analysis, dependency scanning, container scanning, deployment, and dynamic application security testing.

## Tech Stack

### Application

- **Frontend:** Vite + React
- **Backend:** FastAPI + Python
- **Python package management:** `uv`
- **Database:** Neon PostgreSQL
- **Reverse proxy:** Nginx
- **Containers:** Docker + Docker Compose

### CI/CD & DevSecOps

- **Jenkins** — CI/CD orchestration
- **Jenkins Shared Library** — reusable Groovy pipeline steps
- **SonarQube** — SAST / code quality
- **OSV-Scanner** — dependency/SCA scanning
- **Trivy** — Docker image vulnerability scanning
- **OWASP ZAP** — DAST against the running application

## CI/CD Pipeline

The pipeline is:

```
Code
  ↓
SonarQube
  ↓
Quality Gate
  ↓
OSV-Scanner
  ↓
Docker Build
  ↓
Trivy
  ↓
Deploy
  ↓
OWASP ZAP
```

### 1. Code

Jenkins checks out the application repository from GitHub.

The pipeline uses a Jenkins Shared Library:

```groovy
@Library('my-shared-library') _
```

This keeps the Jenkinsfile small while implementation details live in reusable Groovy steps.

### 2. SonarQube

SonarQube performs static analysis and code-quality checks.

The project currently has analysis for languages/configurations including Python, JavaScript/TypeScript, CSS, HTML, YAML, JSON and Dockerfiles.

Example:

```groovy
stage("SonarQube") {
    agent {
        label "ec2-sonar"
    }
    steps {
        code("https://github.com/arnavsx3/anon-feedback.git")
        sonarScan("SonarQube-server", "anon-feedback")
    }
}
```

### 3. Quality Gate

Jenkins waits for SonarQube to finish processing the analysis:

```groovy
stage("Quality Gate") {
    steps {
        timeout(time: 10, unit: 'MINUTES') {
            waitForQualityGate abortPipeline: true
        }
    }
}
```

If the configured SonarQube Quality Gate fails, later stages do not run.

### 4. OSV-Scanner

OSV-Scanner checks the project's dependency manifests/lockfiles against the OSV vulnerability database.

Current project dependency files include:

```
backend/uv.lock
frontend/package-lock.json
```

The scan is performed recursively:

```bash
osv-scanner scan source --recursive .
```

Jenkins also generates:

```
osv-report.json
```

and archives it as a build artifact.

Conceptually:

```
Python dependencies + Node dependencies
                  ↓
             OSV-Scanner
                  ↓
            osv-report.json
```

OSV focuses on application dependencies, while Trivy later scans the complete Docker images.

### 5. Docker Build

All three services are built as Docker images:

```
anon-feedback-backend
anon-feedback-frontend
anon-feedback-nginx
```

The build is driven by:

```bash
docker compose -f docker-compose.yml build
```

Nginx uses an unprivileged image:

```dockerfile
FROM nginxinc/nginx-unprivileged:alpine

COPY nginx.conf /etc/nginx/nginx.conf
```

Inside the container Nginx listens on port 8080.

Compose maps:

```yaml
ports:
  - "80:8080"
```

Therefore:

```
Internet → EC2 :80 → Nginx :8080
```

### 6. Trivy

After the images are built, Trivy scans every image returned by:

```bash
docker compose config --images
```

Current command:

```bash
trivy image \
    --severity HIGH,CRITICAL \
    --ignore-unfixed \
    <image>
```

For this learning project, Trivy is currently reporting-only. It does not block the pipeline on findings.

That means Trivy:

- scans the images
- reports vulnerabilities
- ignores vulnerabilities that do not have a fix
- does not fail Jenkins just because findings exist

For a production pipeline, the failure policy should be tightened according to the project's risk tolerance.

### 7. Deploy

The application is deployed on `ec2-sonar` using Docker Compose.

The backend environment file is injected from Jenkins credentials during deployment rather than stored in Git.

Then:

```bash
docker compose -f docker-compose.yml up -d
```

The resulting services are:

```
anon-feedback-nginx-1
anon-feedback-frontend-1
anon-feedback-backend-1
```

### 8. OWASP ZAP

OWASP ZAP performs Dynamic Application Security Testing (DAST) against the running application.

ZAP runs in Docker and joins the Compose network:

```bash
docker run --rm \
  --network anon-feedback_default \
  -v "$PWD:/zap/wrk/:rw" \
  ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py \
  -t http://nginx:8080 \
  -r zap-report.html \
  -J zap-report.json \
  -I
```

Because ZAP is attached to the same Docker network, it can reach the Nginx service using:

```
http://nginx:8080
```

The scan generates:

```
zap-report.html
zap-report.json
```

and Jenkins archives both files.

The baseline scan uses `-I` so warnings do not make the test project's pipeline fail.

## Jenkins Shared Library

The Jenkinsfile uses reusable functions such as:

```
code()
sonarScan()
osvScan()
buildDocker()
trivyImageScan()
injectEnv()
deploy()
zapScan()
```

The shared library is configured in Jenkins as:

```
my-shared-library
```

Typical structure:

```
jenkins-shared-repository/
│
├── vars/
│   ├── sonarScan.groovy
│   ├── osvScan.groovy
│   ├── buildDocker.groovy
│   ├── trivyImageScan.groovy
│   ├── injectEnv.groovy
│   ├── deploy.groovy
│   └── zapScan.groovy
```

## Example Jenkinsfile

```groovy
@Library('my-shared-library') _

pipeline {

    agent any

    stages {

        stage("Code") {
            steps {
                code("https://github.com/arnavsx3/anon-feedback.git")
            }
        }

        stage("SonarQube") {
            agent {
                label "ec2-sonar"
            }
            steps {
                code("https://github.com/arnavsx3/anon-feedback.git")
                sonarScan("SonarQube-server", "anon-feedback")
            }
        }

        stage("Quality Gate") {
            steps {
                timeout(time: 10, unit: 'MINUTES') {
                    waitForQualityGate abortPipeline: true
                }
            }
        }

        stage("OSV Scanner") {
            agent {
                label "ec2-sonar"
            }
            steps {
                osvScan()
            }
        }

        stage("Build") {
            agent {
                label "ec2-sonar"
            }
            steps {
                buildDocker()
            }
        }

        stage("Trivy Image") {
            agent {
                label "ec2-sonar"
            }
            steps {
                trivyImageScan()
            }
        }

        stage("Deploy") {
            agent {
                label "ec2-sonar"
            }
            steps {
                injectEnv("anon-feedback-env")
                deploy()
            }
        }

        stage("ZAP") {
            agent {
                label "ec2-sonar"
            }
            steps {
                zapScan()
            }
        }
    }
}
```

## Running the Application

### Requirements

You need:

- Docker
- Docker Compose
- Git
- A Neon PostgreSQL database
- Jenkins
- A Jenkins agent with Docker access
- SonarQube
- OSV-Scanner
- Trivy

ZAP is run from its Docker image, so it does not need to be installed directly on the EC2 host.

### Run with Docker Compose

From the repository root:

```bash
docker compose up -d
```

Check the services:

```bash
docker compose ps
```

or:

```bash
docker ps
```

The application is served through Nginx on port 80:

```
http://YOUR_EC2_PUBLIC_IP
```

## Security & Secrets

### Environment variables

Real environment files and credentials should not be committed to Git.

The pipeline injects the backend environment through Jenkins Credentials during deployment:

```
Jenkins Credentials
        ↓
backend/.env
        ↓
Docker Compose
        ↓
Backend
```

### Network exposure

Only Nginx is publicly exposed:

```
80 → Nginx
```

Frontend and backend communicate through the internal Docker network.

### Non-root Nginx

The Nginx service uses:

```
nginxinc/nginx-unprivileged
```

so the web server does not need to run as the root user.

## What Each Security Tool Does

```
                 Security Coverage

Source Code
    │
    └── SonarQube
         SAST / code quality

Dependencies
    │
    └── OSV-Scanner
         SCA / dependency vulnerabilities

Docker Images
    │
    └── Trivy
         OS / package / image vulnerabilities

Running Web App
    │
    └── OWASP ZAP
         DAST / web security testing
```

Together these tools cover several major DevSecOps checkpoints:

```
Code → Dependencies → Containers → Running Application
```

This is a core learning-oriented DevSecOps stack, not a complete production security program. Areas such as secret scanning, IaC security, SBOMs, image signing, runtime security, cloud security, monitoring, and more advanced authentication/security testing are additional topics.

## Project Goal

The application is intentionally simple so the DevSecOps workflow remains the focus.

The goal is to understand how security checks can be integrated directly into CI/CD:

```
Developer pushes code
        ↓
      Jenkins
        ↓
   Static analysis
        ↓
 Dependency scanning
        ↓
    Docker build
        ↓
 Container scanning
        ↓
     Deployment
        ↓
   Dynamic testing
```
